## 3. Архитектурное решение и подробные находки

### 3.1. Что действительно построено

```text
HTX WebSocket / REST
    -> collector -> Redis: ticker cache
                 -> Postgres: journal, alerts, forecast evaluation
                 -> scheduler -> services из chatbot

Telegram -> chatbot + chatbot_wored -> routing -> Ollama / fallback APIs
                                   -> Postgres / Redis
                                   -> internal WebUI prediction API

Browser / Mini App -> webui -> HTX / Postgres / Redis
                           -> свой prediction_engine -> Ollama / NVIDIA
                           -> прямые операции с sim_positions

HERMES на хосте -> собственный профиль и provider configuration
Telegram HERMES bridge -> Redis queue -> host task worker -> whitelist команд

hypercube -> отдельный gateway; участие в текущем inference WORED не подтверждено
```

Сильные стороны: сбор рынка отделён от Telegram; PostgreSQL подходит для истории, связей и транзакций; Redis уместен для горячего состояния; прогнозы сохраняют model_id, роли и отдельные точки; есть каркас state machine сессии, расчёта издержек и риск-ограничений; административный HERMES использует whitelist команд. Основной Dashboard действительно показывает график, индикаторы и свежие записи журнала.

Слабая сторона — сервисы выделены инфраструктурно, но недостаточно отделены как программные модули. `collector` монтирует исходники `chatbot` и `webui`, меняет PYTHONPATH и импортирует их внутренности. `webui/app.py` разросся до более 4300 строк: HTML, auth, SQL, прогнозы, сделки, сессии и метрики находятся в одном модуле. Три места определяют работу с AI: chatbot router, WebUI prediction engine и session manager; HERMES добавляет четвёртую конфигурацию.

Для персонального продукта я оставил бы текущие сервисы и PostgreSQL. Переход на SQLite или увеличение числа микросервисов сейчас не решает обнаруженные проблемы. Нужны общий пакет контрактов, единый service layer выполнения, очередь задач и единый учёт вызовов провайдера.

### 3.2. Приоритеты

P1 — исправить до использования продукта как надёжного помощника и до внешнего доступа. P2 — исправить в следующем цикле стабилизации. P3 — улучшение после восстановления корректности. Ниже отдельно указаны воспроизведение, live-факт и вывод из кода.

#### F01 · P1 · «Новый прогноз» не запускает вычисление

**Код:** `D:\WORED\webui\app.py:4046–4089`, особенно 4075–4088.

Функция создаёт локальный `BackgroundTasks()`, добавляет задачу, затем возвращает обычный dict. Объект не инжектирован FastAPI и не прикреплён к Response. Поэтому `run_prediction_request_async` не исполняется, хотя пользователь получает `ok=true`, `pending` и обещание обновления через минуту.

**Воспроизведено:** POST через TestClient вернул 200; await_count фоновой функции равен 0. **Live-подтверждение:** в БД пять pending-запросов, все с `source=command-deck`: #108, #111, #115, #117, #118; два самых старых — с 6 сентября. Forecast Lab показывает для #118 «running in the background» и 0/0 моделей.

**Исправление:** сначала корректно прикрепить BackgroundTasks; затем перевести расчёт в долговечную очередь с job_id, deadline, retry и восстановлением после рестарта. Добавить уникальный idempotency key на запуск и состояния queued/running/partial/completed/failed/expired.

**Приёмка:** один клик создаёт одну задачу; модель вызывается; ответ появляется; повтор отправки не создаёт дубликат; потерянная задача становится failed либо повторяется по явной политике. Зависшие исторические записи исправлять отдельно с журналом изменений.

#### F02 · P1 · Сессия получает искусственные нули вместо индикаторов

**Код:** `chatbot/services/session_manager.py:59–112`; `collector/indicators/calculator.py:32`.

`build_market_context()` вызывает `calculate_indicators(symbol, tf)`, но функция принимает только symbol. Исключение подавляется, и четыре timeframe остаются с нулевыми RSI/MACD/ATR и `risk_flags=['none']`. Дополнительно калькулятор возвращает `rsi_14`, а потребитель ищет `rsi`; ATR и trend калькулятор не возвращает. В контейнерах chatbot/webui каталог collector вообще не смонтирован, поэтому динамический импорт там не обеспечивает нужный контракт.

**Воспроизведено:** точная функция из исходника, реальный калькулятор, подставной Redis с ненулевой ценой → нули на всех четырёх периодах. В live-плане сессии текст прямо объясняет no-trade нулевыми индикаторами, хотя основной AI Journal показывает ненулевые RSI и MACD.

**Следствие:** объяснение исходного отчёта «самоустранилось после накопления данных» не подтверждается для этого пути. Неизвестные данные выдаются модели за измеренный нулевой сигнал.

**Исправление:** единый MarketSnapshot с периодом, временем, source, quality и nullable-индикаторами. Collector публикует готовые измерения; потребители не импортируют его код. Явно преобразовать `1m` в HTX `1min`, `1h` в `60min`. При недостатке данных возвращать unavailable и блокировать аналитическое решение на уровне политики.

**Приёмка:** один и тот же snapshot в журнале, WebUI и запросе модели; отсутствующие RSI/ATR никогда не становятся нулём; при недоступности источник отмечен красным и объяснён пользователю.

#### F03 · P1 · Авторизация и пользовательская идентичность не едины

**Код:** `webui/app.py:3634`, `3884`, `3891`, `4092`; auth helpers 237–335; Telegram helper 2788–2838; позиции 3947–4034.

Command Deck page, агрегированный API и briefing не вызывают auth guard. Это не свойство standalone HTML и не проблема наследования Jinja: проверка находится в обработчиках маршрутов и должна вызываться явно.

**Воспроизведено при WEBUI_AUTH_ENABLED=true:** `/alerts` → 303 на login, `/command-deck` → 200, `/api/command-deck` → 200 без сессии.

Endpoints открытия/закрытия позиции и quick forecast guard вызывают, поэтому утверждать, что они обходят включённую session auth, нельзя. Однако при фактически используемом local mode guard пропускает всех. Compose публикует 8080, 5432 и 6379 на всех интерфейсах; Docker подтверждает `0.0.0.0`. Redis связан в том числе с host-level очередью HERMES. Tunnel-контейнер работает; доступность с внешнего интернета отдельно не тестировалась.

В новой форме `user_id=0`; backend принимает user_id из тела. Close ищет позицию только по id, без владельца. Telegram verifier по умолчанию отключён; в его реализации не проверяется возраст auth_date, а Command Deck не передаёт initData.

**Исправление:** централизованный guard всех API, проверка Telegram initData и auth_date на сервере, единый Principal, ownership в SQL, отдельное разрешение администратора. Служебные БД/Redis оставить внутри Docker-сети либо bind к loopback. Внешний доступ открывать только после тестов отказа в доступе.

**Приёмка:** анонимный запрос не получает данные сессии и не меняет симулятор; пользователь A не читает/закрывает позицию B; подмена user_id игнорируется; просроченная Telegram подпись отвергается.

#### F04 · P1 · Новый торговый маршрут обходит доменные проверки

**Код:** `webui/app.py:3955–3979`; `chatbot/services/sim_engine.py:57`.

Открытие напрямую INSERT-ит sim_positions: нет enum-направления, положительной маржи, допустимого плеча, проверки пользователя или связанного бюджета. При этом preview нормализует часть значений, а commit использует другую логику. В таблице нет CHECK, которые бы компенсировали эти пропуски.

**Воспроизведено на mock DB:** direction=`invalid`, leverage=1000, margin=-5 приняты с HTTP 200. Рабочие некорректные позиции не создавались.

**Исправление:** типизированная Pydantic-модель и общий execution service для Telegram и WebUI. Денежные расчёты — Decimal с заданным округлением. Preview и commit используют одну функцию политики, commit перепроверяет свежесть цены. Добавить idempotency и атомарный переход статуса при закрытии.

**Приёмка:** некорректные запросы → 422/409; два одновременных закрытия дают ровно один переход; единые проверки риска для всех входов.

#### F05 · P1 · PnL и ликвидация создают неверную картину симуляции

**Код:** `webui/app.py:3906–3943`, `4019–4034`; `collector/scheduler/sim_monitor.py`.

При плече 200x используемая формула даёт `1/200 = 0.005`, то есть цена ликвидации равна цене входа. Это воспроизведено и локальным mock-тестом, и read-only live-preview: distance=0%. При этом UI разрешает подтвердить такую заявку.

В форме показываются сценарии ±5% даже при расстоянии до ликвидации 0.5%; не объясняется, что для isolated-позиции сценарий движения против позиции не достигается как обычный продолжающийся PnL. Close Command Deck записывает raw PnL в realized_pnl без вычета входной/выходной комиссии и funding, тогда как sim monitor рассчитывает net с вычетами. Одна колонка БД получает разный финансовый смысл в зависимости от пути закрытия.

**Исправление:** единая версия модели издержек и ликвидации; gross, fees, funding, slippage и net хранить раздельно. Не разрешать комбинацию с maintenance margin и издержками, при которой позиция неплатёжеспособна при открытии. Сценарии за барьером ликвидации показывать как ликвидацию. Если заявляется соответствие HTX perpetual, отдельно сверить mark price, contract rules и maintenance tiers с документацией конкретного инструмента. Текущий review не сертифицирует такую эквивалентность.

#### F06 · P1 · Истёкший прогноз и повторный арбитр выдают ложный консенсус

**Код:** `webui/app.py:3651–3722`, `1516`, `1582–1585`; `prediction_engine.py:899` и далее, функция generate_role_prediction_bundle.

API выбирает последний request со status=active без проверки конца горизонта. В снимке 14:44 UTC выбран #116, созданный 07:59 UTC, последняя цель которого — 11:59 UTC. В браузере текущие часы 21, а «будущие» свечи идут как 15, 16, 17, 18 по местному времени.

Role bundle уже запускает arbiter, после чего вызывается finalize_oracle_prediction ещё раз. В live #116 есть bull GLM-5.1, bear GLM-5.2 и два arbiter MiniMax M3. Агрегатор считает все четыре model_run голосами и показывает 3/4. Повтор арбитра получает двойной вес; кроме того, арбитр уже видел ответы других ролей, поэтому голоса не независимы.

**Исправление:** один канонический арбитр на revision; revision_id, as_of, target_time, valid_until; истёкшие данные отдельно; агрегация по актуальной версии роли. Финальное решение арбитра и ответы двух оппонентов показывать раздельно. Не изображать дискуссионные роли как независимую статистическую выборку.

**Приёмка:** ровно один arbiter на версию; истёкший запрос не выглядит рекомендацией сейчас; сортировка временной оси монотонна; заголовок сообщает возраст и горизонт.

#### F07 · P1 · Текущие метрики не доказывают превосходство моделей

**Код:** `collector/predictions/evaluator.py:145–172`; `webui/app.py:3833–3848`.

Формула `max(0,100-price_error_pct) + 10 за направление + 10 за диапазон`, cap 100, почти насыщается при обычном малом движении. Даже неверное направление при ошибке цены 0.5% даёт 99.5 без бонусов. Это не вероятность успеха и не качество торговой стратегии.

**Live SQL:** MiniMax M3 arbiter — 40 точек / 8 requests, средний score 99.94, 35 точек ровно 100; GLM-5.1 bull — 38 / 10, 99.78; GLM-5.2 bear — 38 / 10, 99.71. На Command Deck «Worker 72.7%» — лишь 8/11 точек. Показатели агрегируются по model_key за всю историю, объединяя сменявшиеся модели и версии оценщика. Это объясняет часть разрыва между историческими score и новыми почти 100.

Дополнительная проблема: evaluator выбирает close свечи, начало которой <= target_time, когда exact match не найден. Для цели внутри часа оценка вскоре после цели использует ещё незакрытую свечу; поздняя оценка может использовать её финальный close, который включает время после цели. Результат зависит от момента запуска оценщика.

**Исправление:** определить точный контракт цели: цена на момент либо close конкретной закрытой свечи; сохранять as-of data. Отдельно считать error в bps, directional balanced accuracy, калибровку confidence, покрытие и ширину интервала, net PnL после всех издержек. Сравнивать с no-change и простым детерминированным baseline. Разбивать по symbol, horizon, model/version, prompt/version и evaluator/version; хранить размер выборки в независимых запросах, не только точках.

**Приёмка:** walk-forward проверка с непересекающимися временными окнами; отсутствует утечка будущих данных; одинаковый прогноз получает одинаковую оценку при повторном запуске; вывод о premium делается по сравнению на одинаковых snapshots, с учётом неопределённости и стоимости.

#### F08 · P1 · Учёт и квоты существуют как файлы, но не замыкают execution

**Код:** `chatbot/ai/token_accounting.py`, `chatbot/ai/quota.py`, `chatbot/ai/router.py:132–191`, `webui/prediction_engine.py:654–745`.

По поиску активных исходников у log_ai_request нет runtime callers, check_quota используется только внутри get_quota_status, record_usage вызывается из неинтегрированного accounting helper. В БД ai_usage_log=0 строк, usage_log=1. Native Ollama adapter извлекает строку ответа и отбрасывает token counts, cached counts, duration и finish reason.

Даже отдельно quota helper не реализует обещанный контракт: общий суточный request count применяется ко всем tiers, worker не блокируется при исчерпании, нет резервирования до конкурентного запроса и нет месячного бюджета провайдера. Общего лимитера для двух ботов, WebUI, collector и HERMES не обнаружено. Worker fallback может переходить в analyst/premium через expand_fallback_tiers без validation gate.

**Исправление:** общий ProviderCall gateway либо библиотека с ledger; request_id создаётся на входе, каждая попытка имеет attempt_id. Перед вызовом — атомарное резервирование средств/лимита, после — сверка реального usage. Отдельные бюджеты инженера HERMES и market-runtime. Включённые в подписку кредиты также являются ограниченным бюджетом.

**Приёмка:** любой вызов провайдера отражён в ledger, включая неудачи и fallback; после исчерпания потолка новые вызовы отклоняются; отмена/timeout не теряют расход; paid/premium доступен только по утверждённой политике и результату оценки.

#### F09 · P2 · Контракт ответа модели и readiness недостаточны

**Код:** `webui/prediction_engine.py:671–701`, `742–745`; `chatbot/ai/router.py:175–182`; `session_manager.py:590`.

Native adapter ищет content, затем reasoning. Официальный native API описывает отдельное `message.thinking`, а также `done_reason` и token counts. Это не основание считать thinking готовым ответом. Утверждение отчёта, что reasoning-модели по определению кладут весь ответ в reasoning, не подтверждено общей спецификацией. При малом output budget модель могла не дойти до финального ответа; без finish reason точную причину не определить. [Ollama Chat API](https://docs.ollama.com/api/chat).

В chatbot общий router возвращает badge и content без проверки непустоты: при content=None получится пользовательский текст с None вместо fallback. Исправление reasoning в session_manager не исправляет router. Prediction configs ограничивают вывод 2000 токенами даже при 48 шагах и рассуждении; вероятность усечения должна проверяться контрактным тестом, а не догадкой.

**Исправление:** нормализованный ответ с final_text, finish_reason, usage, tool_calls, provider/model; строгая валидация итогового JSON и бизнес-ограничений. Capability matrix по endpoint. Ограниченные schema-repair retries с учётом расхода. По актуальной официальной документации Ollama Cloud не поддерживает structured outputs; рекомендация просто добавить JSON Schema в format не является гарантированным решением для Cloud. [Structured Outputs](https://docs.ollama.com/capabilities/structured-outputs).

#### F10 · P2 · Почасовая коррекция содержит незакрытые дефекты

**Код:** `collector/predictions/evaluator.py:260–345`.

Путь снова превращает btcusdt в btc-usdt, хотя соседний evaluator уже исправлен; передаёт aware datetime в запрос по timestamp without time zone; в конце вызывает append_prediction_model_result без импорта/определения в модуле. Также смешивает horizon_hours с количеством шагов для нечасовых периодов. Эти препятствия видны в исходнике, но live-коррекция намеренно не запускалась из-за записи в БД и расхода модели.

**Исправление:** отдельный сервис revisions с контрактными тестами времени, символов и вызова persistence. Отказ должен отмечать failed correction, а не оставлять пользователя с видимостью актуального плана.

#### F11 · P2 · Свечи отображаются с неверной семантикой

**Код:** `webui/templates/command_deck.html`, renderCandles; `webui/templates/predictions.html:496`.

В Command Deck историческое тело рисуется от нижней границы графика до max(open,close), а не между open и close. Для прогнозов тело — столбик до средней цены. Это столбчатый рисунок, визуально похожий на свечи, но не корректный OHLC. В Forecast Lab любая target_time округляется вверх по 3600 секундам; для 15m несколько целей получают одинаковое время, что несовместимо с отдельными candlestick точками. Последнее — подтверждено анализом выражения, не запуском нового 15m-прогноза.

**Исправление:** исторический OHLC выводить без преобразования формы, прогноз — линией/диапазоном с явной легендой. Если оставлять синтетические свечи, обозначить, откуда взяты open/high/low/close. Шаг временной сетки брать из timeframe, не захардкодить 1h.

#### F12 · P2 · Зелёный health не означает здоровую функцию

**Код:** `webui/app.py:1640–1677`; `docker-compose.yml`; `collector/scheduler/pipeline_jobs.py:38–68`.

collector_feed означает лишь, что последняя запись ai_journal моложе 20 минут. Это не freshness котировки, не доступность модели, не жизнеспособность scheduler и не успех pipeline. `/api/health` возвращает JSON с HTTP 200 и при false-компонентах, тогда как Docker healthcheck проверяет только успешное получение HTTP. Отдельный stale guard при отсутствии timestamp считает существующие данные свежими.

**Исправление:** отделить liveness, readiness и качество данных; readiness для обязательной зависимости отдаёт 503; показывать время последнего тика, корректного snapshot, расчёта, ревизии и ошибки. Добавить heartbeat задач и счётчики stuck jobs. Неизвестная свежесть должна блокировать execution, а не считаться fresh.

#### F13 · P2 · Регрессии не задерживаются на тестовом барьере

**Факт:** 13 упавших тестов в WebUI/chatbot и ошибка collection collector. Часть — устаревшие ожидаемые модели и сигнатуры, часть — рассогласованный контракт internal token. Это не 13 доказанных production-багов, но объективное отсутствие зелёного регрессионного контроля.

99 Python-файлов разобраны AST без SyntaxError; это не lint и не проверка типов. Найдены две верхнеуровневые `_route_trade_sim` в router.py:327 и :509 — вторая затеняет первую. Зависимости задаются нижними границами `>=`, воспроизводимого lock для core не обнаружено; Dockerfile смешивают Python 3.9 и 3.11. В core не обнаружен настроенный единый lint/typecheck/CI pipeline. Lock и более развитые тесты hypercube не покрывают этот runtime автоматически.

**Исправление:** один поддерживаемый runtime Python, lock dependencies, CI по компонентам, тесты общего domain layer и browser smoke. Сначала восстановить смысл тестов, потом требовать зелёный статус, а не удалять падающие проверки.

#### F14 · P2 · Документация описывает несколько несовместимых состояний

README/AGENTS говорят о пяти сервисах, compose содержит шесть с chatbot_wored; tunnel поднят отдельно. README рекомендует analyst deepseek-v4-pro, live prediction analyst — glm-5.1, все три роли chatbot — minimax-m3. Два HERMES-профиля используют разные default-модели. В AGENTS предложен `docker compose restart` для применения изменённых env — перезапуск существующего контейнера не пересоздаёт его конфигурацию env. Makefile содержит разрушительный clean с down -v и неисполняемый как единый интерактивный сценарий restore с отдельными recipe shells.

**Исправление:** generated runtime manifest: commit, image digest, config hash, model role mapping, environment names, активные сервисы и endpoints; runbook отдельно для Windows/WSL. Secrets не выводить. Применение env описать через контролируемое пересоздание нужного сервиса. Настройку refresh provider registry и недельный changelog оформить реально исполняемым процессом: в проверенных core docs/scripts такой обязательной подсистемы не обнаружено.

### 3.3. HERMES и «несколько специалистов»

Есть три разных понятия, которые нельзя смешивать:

1. **Инженерный агент HERMES** работает на хосте и имеет инструменты для сопровождения. Текущий Windows-профиль wored: default glm-5.2, reasoning deepseek-v4-pro, provider ollama-cloud. Проверенный WSL-профиль: default kimi-k2.7-code, reasoning deepseek-v4-pro, provider ollama-cloud. Это конфигурационные факты; конкретный последний inference winner не установлен.
2. **HERMES bridge из Telegram** — whitelist команд через Redis и host worker. В проверенном chatbot флаг включён. Этот мост сам по себе не является LLM-командой из нескольких автономных инженеров; он запускает заданные диагностические команды. Факт постоянно работающего consumer не установлен отдельным end-to-end заданием.
3. **Специалисты прогнозирования** — последовательные вызовы bull, bear, arbiter с разными prompts. В активном prediction configuration: GLM-5.1, GLM-5.2, MiniMax M3. Worker DeepSeek V4 Flash настроен, но не участвует в текущем трёхролевом bundle. Все роли обычного chatbot используют MiniMax M3 с разными бюджетами вывода.

Само число названных ролей не даёт надёжности. Bull/Bear полезны как проверка альтернативных гипотез. Арбитр должен сводить аргументы, но не получать второй голос в majority vote. Для независимого QA нужен специалист, который проверяет snapshot, расчёты и тесты, а не только ещё раз прогнозирует цену. За correctness должен отвечать детерминированный код и тестовый барьер, а не личность агента.

Gateway endpoints `/healthz` и `/dashboard/active-route` на localhost:8000 не ответили за 3 секунды. Это предел проверки, а не доказательство отсутствия всех возможных gateway на хосте. Использование `hermes/active-slot` текущими двумя проверенными профилями не обнаружено.

### 3.4. Ollama Pro и модельная стратегия

Официальная публичная страница на дату проверки: Pro — $20/мес., $60 включённых usage credits в месяц, 3 одновременных запроса. Поэтому принадлежность конкретной подписки к новой схеме нужно подтвердить в кабинете; этот аудит её не предполагает. **Pro нельзя проектировать как неограниченный бесплатный endpoint.** [Тариф Ollama](https://ollama.com/pricing).

## 8. Ожидаемые результаты исправлений и критерии готовности

1. Ни одна задача не висит pending сверх заданного deadline без понятной причины и маршрута восстановления.
2. Любое число в модели и UI имеет определённый смысл, source, as_of, единицы и версию расчёта; unknown отделён от zero.
3. Один request/revision содержит ровно определённый набор ролей, один финальный arbiter и неизменяемый baseline snapshot.
4. Симулятор даёт одинаковый результат независимо от Telegram/WebUI/monitor пути; риск и владельцы проверяются сервером.
5. Каждый provider attempt отражается в durable ledger, а суммарный лимит аккаунта проверяется до вызова.
6. Новые provider/model допускаются по контрактному тесту; дорогой маршрут — дополнительно по сравнению с baseline и бюджету.
7. Все обязательные тесты зелёные; свежий запуск из lock/config воспроизводится на отдельной тестовой БД, не на пользовательских данных.
8. UI явно отвечает: данные свежие или нет, прогноз актуален или нет, почему нет сделок, симуляция ли это, что произойдёт после нажатия.

Это критерии следующего релиза, а не утверждение, что они достигнуты текущим аудитом.

## 10. Остаточные риски и следующий шаг

**Первый пакет стабилизации:** F01, F02, F03, F04–F08 и тесты, которые воспроизводят их текущие последствия. Приоритет внутри пакета: закрыть внешний доступ к небезопасным путям; восстановить запуск задач и данные; привести ledger/метрики/симуляцию к единому контракту. Не начинать с добавления новых агентов или нового большого экрана.

**Второй пакет:** общие adapters и contracts; исправление hourly corrections, health/readiness, migrations, lock/CI; единый журнал model/provider attempts и policy.

**Третий пакет:** постепенно выровнять существующие экраны: актуальное состояние первым, симуляция и издержки явно, история вторична, техническая диагностика отдельно. Сохранить рабочие графики, палитру и текущие маршруты.

**После этого:** провести сопоставимую оценку моделей и стратегий на историческом walk-forward наборе, затем ограниченный paper-trading период. Сколько бы специалистов ни участвовало, изменения должны проходить один и тот же независимый тестовый барьер. Ключевое улучшение здесь — общая проверяемая система выполнения, а не более длинная цепочка LLM.

Осталось вне доказанной области: реальный баланс/тип подписки Ollama, inference доступность всех fallback, точный активный процесс HERMES и его последний winner, Telegram WebView end-to-end, полный security/WCAG-аудит, fresh build, полный код hypercube/foresight и длительный backtest. Никакие из этих пунктов не обозначены как успешно пройденные.
