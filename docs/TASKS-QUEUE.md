## Открыто, по приоритету обзора

### P5 = M8. Готовый прогноз не виден на `/`

Свежая находка 2026-09-22, описана в обзоре (§2, M8). `api_command_deck`
(`app.py:3806-3808`) берёт запрос с `status='active'` и обязательной будущей
точкой, а очередь по завершении пишет `completed`: в прод-БД из 46 `active`-запросов
будущих точек нет ни у одного, а с будущими точками живёт 1 запрос и он
`completed`. Там же `agreement = N/N` считается только по выжившим ролям (та же
природа, что в M7), а NULL фитиль (340 из 855 точек) уходит в график как ноль через
`float(cr["predicted_low"] or 0)` — на пути трейдера это снято `b00351d`, на `/` — нет.
Требует решения владельца о том, какой прогноз считать витриной, прежде чем править код.

### M5 (из бывшего P4). Карта ролей в `AGENTS.md` расходится с прод-окружением

`OLLAMA_ANALYST_MODEL=glm-5.1` против «analyst = `deepseek-v4-pro`»; дефолт в коде
тоже `glm-5.1`, так что расхождение не сводится к одному `.env`. Практический
эффект: «бык» систематически теряет ~60 с на таймящемся `glm-5.1`. Сюда же строка
`AGENTS.md` про NVIDIA NIM как активный fallback-tier — с `f5ffabf` tier по
умолчанию выключен (`NVIDIA_NIM_ENABLED`). **Ждёт решения владельца:** и `.env`, и
`AGENTS.md` без явного слова не меняются. Правка M7 из того же P4 выполнена — см.
«Закрыто».

### Бэкфилл `partial` по историческим запросам

#127/#133/#134/#137 остаются с `execution_state='completed'` в БД: затёртое
очередью значение не отличить от настоящего. Если нужна честная ретроспектива —
это отдельный `UPDATE` (`status='completed' AND execution_state='completed' AND
EXISTS (фейловый прогон роли)` → `partial`); он правит прод-данные, поэтому без
явного слова не выполняется.

## Хост: локальная модель bonsai-27b

Сделано 2026-09-22 (подтверждён только пункт «supervise + healthcheck»):
`scripts\bonsai_health.ps1` (коды 0/1/2), `scripts\bonsai_guard.ps1` (стартует
только когда порт молчит, чужие процессы не убивает), `scripts\install_bonsai_supervision.ps1`
(таск `WORED-Bonsai-8088`: логон + каждые 5 мин, `IgnoreNew`, рестарт 3× через 1 мин).
Замеры: health 0 на 8088; негативный тест — health 2 на 11434 с текстом про чужое
хранилище; recovery-path проверен на запасном порту 8089 (сервер поднят, модель видна,
тестовый процесс остановлен), живой 8088 не трогался.

Открыто, каждое требует отдельного «да»:

1. Чистый перезапуск `ollama app.exe` из меню «Пуск» — после него `bonsai-27b` станет
   виден в UI приложения (сейчас `11434/api/tags` пуст).
2. Удаление пустых `D:\WORED\blobs` и `D:\WORED\manifests` плюс `.gitignore` на них.
3. Доступ из Docker: 8088 слушает только `127.0.0.1`, а в контейнере
   `LOCAL_LLM_BASE_URL=http://127.0.0.1:8088` — это адрес самого контейнера. Нужны
   bind на `0.0.0.0`, `extra_hosts` в `docker-compose.yml` и `host.docker.internal`
   в `.env`. Риск: API Ollama без авторизации станет доступен в локальной сети.
4. `LOCAL_LLM_ROLES` в `.env` пуст — ни одна роль локальную модель не использует.
   Включать — отдельное решение (соседствует с M5).
