# Стабилизация WORED — архитектурное решение

Статус: реализация и проверка в изолированной копии. Рабочие сервисы не изменены.

Сохраняются FastAPI, Telegram, collector, PostgreSQL и Redis. Новые микросервисы не нужны.

1. PostgreSQL хранит параметры и состояние очереди прогнозов. Worker забирает задание с блокировкой строки SKIP LOCKED. Завершение задания и результаты фиксируются одной транзакцией. При остановке процесса транзакция откатывается, задание доступно повторно. Транзакция ограничена таймаутом; внешний вызов модели может повториться после сбоя — exactly-once для внешнего API не обещается.
2. Collector публикует версионированный снимок индикаторов по закрытым свечам. Потребители читают Redis. Отсутствующие значения представлены null, качество и свежесть проверяются перед планированием и новыми входами.
3. Веб-интерфейс является административным, а не многопользовательским торговым сервисом. По умолчанию нужна авторизация. Telegram initData проверяется криптографически, по возрасту и списку администраторов. Публичные исключения перечисляются явно. Изменяющие запросы из браузера проходят проверку Origin.
4. Все HTTP-входы прогноза используют одну очередь. Внутренний API Telegram теперь возвращает 202 и номер сохранённого задания. Бот сразу показывает состояние pending и кнопку проверки. Контракт horizon_hours переводится в число шагов периода; неоднозначные поля и неверные типы отклоняются. Повтор ключа с иными параметрами возвращает 409, повтор прежнего задания работает и при недоступном feed.
5. Интерфейс развивается постепенно: состояние очереди, актуальность прогноза и ошибки. Разметка и палитра сохраняются.

Изменяемые активные пути: webui/app.py, webui/prediction_engine.py, webui/templates/command_deck.html, chatbot/services/session_manager.py, chatbot/integrations/webui_client.py, collector/main.py, collector/indicators/calculator.py, collector/htx/websocket.py, collector/scheduler/pipeline_jobs.py. Новые модули и тесты перечислены в итоговом diff.

Совместимость: миграции только добавляют поля и таблицы. Исторические оценки не переписываются. Старые pending без сохранённых параметров не запускаются автоматически. Доступ после обновления требует WEBUI_ADMIN_PASSWORD и стабильного WEBUI_SESSION_SECRET; внутренние вызовы требуют одинаковый WEBUI_INTERNAL_TOKEN. Пароли не включаются в пакет.

Дополнительно реализованы метрики версии 2, проверка закрытой свечи нужного интервала, общий расчёт комиссий и PnL для sim_positions и защита от повторного закрытия. Оценка 0–100 является эвристической шкалой ошибки, не вероятностью успеха. Для новых оценок сохраняются ошибка относительно неизменной цены и выигрыш относительно этой базы. Старые оценки сохраняют metrics_version=1.

Автоматический пересчёт исторических оценок и исправления внутри первоначального прогноза сняты с расписания. Старые функции обслуживания явно отклоняют вызов. Коррекцию следует оформлять новым запросом; автоматическое создание связанных ревизий пока не реализовано.

Новая политика sim_positions: плечо 1–100, положительные конечные margin/price, комиссия закрытия от фактического номинала выхода, чистый PnL за вычетом входа, выхода и накопленного funding. Сценарии preview ограничиваются модельной ценой ликвидации. Это учебная модель isolated margin, не спецификация биржи. Новые executed_trades используют тот же расчёт с плечом 10/25/50/100. calculation_version=1 сохраняет старые пороги ликвидации и прежний расчёт комиссии выхода для существующих записей; новые создаются с версией 2. Торговая сессия и заявка блокируются при входе, сессия и сделка — при выходе. Сделка, событие и состояние фиксируются атомарно. Закрытие во время paused не возобновляет сессию; liquidation переводит активную сессию в stopped. Модель cross-margin и биржевое исполнение limit-заявок требуют отдельной доработки.

Критерии приёмки: тесты отказа доступа, просроченного Telegram initData, пустого финального ответа модели, устаревших данных, выполнения задания и отката при отмене; проверка синтаксиса Python; lint новых модулей; отдельный интеграционный прогон с PostgreSQL и Docker перед установкой.

Выполнены 94 различных теста, включая 7 HTTP, 8 SQL на реальном PostgreSQL 16.13 и весь webui/tests/test_app.py. Восемь SQL-тестов выполнены отдельно после выдачи сетевого разрешения: PostgreSQL существующего Docker-стека доступен по 127.0.0.1:5432. Тесты используют отдельную БД wored_qa и временные схемы qa_<uuid>; рабочие таблицы не изменялись. Доступ к Docker pipe для этих тестов не нужен. Синтаксис 107 Python-файлов, Jinja-шаблонов и JavaScript Command Deck/login проверен; критические lint-проверки runtime проходят, mypy проходит для шести новых модулей. Контейнерный прогон заблокирован отказом доступа к Docker API из этой сессии.

### Проверка в отдельной среде

Предусловия: Docker Desktop доступен вызывающему процессу; этот checkout существует; для сборки доступны Python package index и Docker registry. Рабочая конфигурация и ключи не нужны.

```powershell
Set-Location 'C:\Users\dolum\Documents\Codex\2026-09-07\files-mentioned-by-the-user-review\work\wored-stable'
docker compose -p wored-qa -f docker-compose.qa.yml up --build --abort-on-container-exit --exit-code-from checks
```

Успех: checks завершается с exit code 0, тесты PostgreSQL и HTTP выполняются без пропусков. QA не публикует порты, использует отдельную БД wored_qa на tmpfs, не подключает рабочие тома и .env. Пароль в QA compose — публичная константа исключительно для одноразовой тестовой БД, не рабочий секрет.

Если Docker API отвечает permission denied, сначала нужен доступ вызывающего процесса к Docker. Если сборка не может загрузить зависимости, необходим доступ к реестрам. Если тест упал, установка запрещена до устранения воспроизводимой ошибки.

### Установка и откат

Установка не выполнена. Сначала должны пройти контейнерные тесты и ревизия открытых симуляционных позиций. Затем нужны резервная копия БД, стабильные WEBUI_ADMIN_PASSWORD/WEBUI_SESSION_SECRET, одинаковый WEBUI_INTERNAL_TOKEN в WebUI и ботах, список TELEGRAM_ADMIN_ID либо TELEGRAM_ADMIN_IDS. Для внешнего HTTPS требуется WEBUI_COOKIE_SECURE=true и точный WEBUI_PUBLIC_BASE_URL. Пароль выбирает владелец; пакет не назначает его автоматически.

Обновление .env требует пересоздания контейнера, а не простого restart. Владелец разрешил исправления и продолжение работы. Установка и рестарт здесь технически недоступны; после восстановления доступа сначала выполняется QA и проверка резервной копии. При откате к старому коду дополнительные таблицы/поля не удаляются; pending новой очереди перестанут обрабатываться до возврата worker. Возврат старой авторизации может снова открыть ранее защищённые маршруты — такой откат нельзя считать безопасным автоматически.

Остаток стабилизации: общие квоты и token ledger, полный тестовый набор ботов/провайдеров, проверка миграции на копии рабочей БД, конкурентные изменения планов и funding, фиксация транзитивных runtime-зависимостей и визуальный прогон UI. Контейнерный QA включает Telegram handler tests и отказывается считаться успешным при любом пропуске обязательных тестов стабилизации.

Вход Mini App реализован обменом initData на подписанную 12-часовую cookie-сессию через /api/auth/telegram с CSRF. HMAC и auth_date проверяются по [официальной документации Telegram](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app). Смена списка администраторов применяется к существующим Telegram-сессиям. Cookie-запросы проходят Origin; только отдельный запрос с валидным X-Telegram-Init-Data аутентифицируется независимо от cookie. Живой прогон Mini App ещё не выполнен.

Результаты отдельных запусков и объединённый JUnit находятся в evidence/ пакета. Контейнерная сборка/smoke и визуальная проверка изменённого интерфейса ещё не выполнены.
