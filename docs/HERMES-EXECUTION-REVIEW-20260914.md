# Проверка исправлений Hermes и нулевых позиций RACHELLO

Дата: 2026-09-14. Объект: @RACHELLO_BOT / Compose `chatbot`; исполнение его Daily Session обслуживает `collector`. Это проверка исходного кода и локальные исправления, не подтверждение активной сессии в PostgreSQL.

## Проверено до блокировки доступа

HEAD `4a438be`: default analyst_ollama изменён на `gpt-oss:120b`, 4000 output tokens, timeout 90 секунд. Реальная env-настройка может переопределять default. `ANALYST_MODEL_CHAIN` сокращён до трёх кандидатов. `f667020` применяет JSONDecoder.raw_decode: корректный объект с лишним текстом в конце теперь может быть разобран. `efd0d6c` нормализует пустой no_trade-план, но одновременно возвращает требование обязательного entry в aggressive-промпт. Оно противоречит разрешению no_trade при несовместимых ограничениях в том же промпте и прежнему контракту; валидатор всё ещё допускает no_trade в aggressive.

В 18:30 Bangkok все шесть контейнеров running; postgres/webui healthy; `/healthz`, `/readyz`, `/api/health` ответили 200, ready=true. Это подтверждение инфраструктуры, не доказательство автоматической торговли. Только chatbot имел свежий uptime около 12 минут; другие три прикладных процесса работали около часа. Применение всех последних изменений ко всем процессам не подтверждено.

Автоматический контроль доступа отклонил read-only чтение Docker-логов и PostgreSQL: исчерпан лимит сервиса проверки разрешений. Обход не выполнялся. Последний план, его validation_status, активные заявки, события и причина отказа текущей сессии не прочитаны. Утверждение commit message о генерации за 11 секунд независимо не подтверждено.

## Подтверждённые дефекты

1. Watch loop учитывал только исполненные действия; причины пропуска `entry_not_confirmed`, `entry_risk_rejected`, `plan_expired` не попадали в пользовательский статус.
2. `_build_status_response` обрезал сообщение до первых шести строк при превышении 12 строк. Важные сведения о торговле и результате исчезали.
3. После SL `execute_exit` переводит сессию в cooldown; штатного перехода по окончании таймера обратно в armed не было. Почасовая публикация также сохраняла cooldown.
4. Уровень подтверждения закрытой свечи использовался и как цена исполнения позднейшего входа. Это могло давать сделке уже недоступную цену.
5. Daily Session Telegram получает spot-тикер и spot-свечи. Отдельный WebUI paper-контур имеет perpetual bid/ask и другое хранилище. Единая реалистичная симуляция между ними не реализована. В просмотренном scheduler отсутствует runner `paper_agents`; сами роли агентов не исполняют сделки.

## Локальные исправления этого прохода

- `chatbot/services/execution_status.py`: heartbeat каждого цикла, причины ожидания/блокировки, число pending/open, расстояние до зоны, ошибки риска, время cooldown. Redis key `session:execution:<session_id>`, TTL 180 секунд; возраст более 60 секунд отображается как неподтверждённая работа исполнителя. Это новый ключ в существующем Redis, без новых env-переменных, портов или SQL-миграций.
- `chatbot/services/session_manager.py`: публикация heartbeat также при пропуске или исключении; выбор действующего плана до попыток входа; возобновление истёкшего cooldown под блокировкой строки, только с актуальным проверенным планом и с аудитом. Конкурирующая пользовательская пауза имеет приоритет.
- Цена подтверждения и цена исполнения разделены: закрытая свеча подтверждает сигнал, текущий тикер задаёт базу simulated fill и повторной проверки риска. Источник всё ещё spot; этот патч не выдаётся за перевод на perpetual bid/ask.
- `chatbot/handlers/pipeline.py`: заголовок «Сессия симуляции», видимые причины нулевых позиций и время проверки, без обрезания до шестистрочного digest. Нет heartbeat — нет утверждения, что исполнитель работает.
- `tests/test_execution_status.py`: девять offline-проверок, включая поздний fill, просроченный план, завершение cooldown, приоритет pause, отсутствие заявок и исключение исполнителя.

## Проверка

Предпосылки: PowerShell в D:\WORED, Python с зависимостями проекта, pytest, ruff и mypy. Внешние AI-провайдеры и Telegram в тестах не вызываются.

```powershell
Set-Location D:\WORED
python -m pytest tests/test_execution_status.py tests/test_session_plan_contract.py tests/stabilization/test_execution_contracts.py tests/stabilization/test_snapshot_consumers.py -q -p no:cacheprovider
python -m ruff check chatbot/services/execution_status.py tests/test_execution_status.py
python -m mypy --follow-imports=silent --ignore-missing-imports chatbot/services/execution_status.py
python -m compileall -q chatbot/services/execution_status.py chatbot/services/session_manager.py chatbot/handlers/pipeline.py
```

Результат: 42 passed, 15 skipped (DB-зависимые проверки), одно предупреждение pytest_asyncio о deprecated API Python 3.14. Новый модуль проходит Ruff/mypy. Детерминированные mock-тесты не заменяют проверку действующей сессии.

## Незавершённое и следующий шаг

Рабочие процессы после этого пакета не перезапускались. Для принятия результата нужны восстановленный доступ к Docker, чтение текущего плана @RACHELLO_BOT и его записанных отказов, загрузка пакета в chatbot/collector, затем наблюдение полного цикла сигнал → simulated fill → закрытие → P&L. При каждом нуле позиций должна быть конкретная актуальная причина. Отсутствие сигнала не обходится принудительным открытием сделки.

Для соответствия реальности остаётся объединение источника котировок, учёта и исполнения Telegram/WebUI: perpetual bid/ask для fill, mark для риска, комиссии, funding, шаг цены/объёма, единая книга сделок. Этот аудит не объявляет эти работы выполненными.

При откате не применять git reset --hard: рабочее дерево содержит ранее внесённые изменения Hermes и Codex. Код этого прохода ещё не развёрнут, поэтому runtime-откат не требуется. Историю сделок и планы не изменять. После восстановления доступа сначала определить точную причину ожидания, затем согласовать загрузку и проверку кода.
