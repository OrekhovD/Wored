## 3. Реестр дефектов

### D1 — BLOCKER — Нет хранилища исторических свечей

Схема `trader_v1_perp_candles` объявлена, писателя нет. Персистятся только `market_tickers` и `alerts`.

Проверка: grep `perp_candles|INSERT INTO .*candle|ohlcv` по `collector`, `chatbot`, `webui`, `forecast_engine`, `paper_trading` → **0 файлов**.

Следствие: невозможен backtest, walk-forward, оценка кандидата. Блокирует D2, D5, D6, D7.

### D2 — BLOCKER — Три реализации обучения, ни одна не подключена

| Компонент | Файл | Вызовов вне файла |
|---|---|---|
| Генератор кандидатов (LLM) | `chatbot/ai/strategy_learner.py:run_strategy_learner` | 0 |
| Статистический валидатор | `paper_trading/learning.py:LearningEvaluator` | только `tests/paper_trading/test_integration.py:198,215` |
| Потребитель правил | `get_latest_strategy_rules` | только `chatbot/ai/strategy_learner.py:108` |
| Живой путь | `webui/app.py:2851-2877` | работает, `source=heuristic_webui`, `status` по умолчанию `candidate` |

Ни `sim_engine`, ни `BaselineV1Strategy`, ни `runner` не читают `strategy_rules`. Система пишет правила и никогда их не применяет. Промоушена `candidate → active` нет ни в одном код-пути.

### D3 — CRITICAL — Две расходящиеся формулы ликвидации

- `chatbot/services/sim_math.py:liquidation_price` (long, v2): `E·(1 − 1/L + f) / (1 − MM)`
- `paper_trading/risk.py:calculate_liquidation_price` (long): `E·(1 − (1/L − MM − f))`

Численная проверка при `entry = 80329.5`, `MM = 0.005`, `taker = 0.0006`:

Расхождение систематическое и асимметричное: `risk.py` ликвидирует лонг раньше, шорт — позже. Выборка, смешивающая эпизоды двух контуров, обучит модель тому, что шорты безопаснее лонгов. Это артефакт кода, а не свойство рынка.

### D4 — CRITICAL — Стратегия только long

`paper_trading/strategy.py:BaselineV1Strategy.evaluate`:

- `regime_bullish()` → `EMA20 > EMA50` на 1h, иначе `return None`
- `confirm_15m()` → `close > EMA20`, иначе `return None`
- триггер → `last.close > prev.high`
- `_build_signal(side="long")`

Слово `short` встречается в файле один раз — в комментарии к `Signal.side`.

Следствие: winrate становится функцией рыночного режима, а не качества модели.

### D5 — CRITICAL — Гейт промоушена статистически несостоятелен

`paper_trading/learning.py:105-200`.

1. **Порог без дисперсии.** Гейт — `candidate_net − baseline_net ≥ 0.001 × capital` (1 USDT на 1000). Сравниваются две суммы без оценки SE. При `min_holdout_episodes = 6` стандартная ошибка разницы на порядок больше порога.
2. **Неверная просадка.** `max_dd = max(e.max_drawdown for e in eps)` — максимум поэпизодных просадок, а не просадка кривой эквити портфеля.
3. **Purge gap — декларация.** Конфиг: `"purge_gap": "max_lookback + hold_time"`. Код: `purge_count = max(1, int(len(sorted) * 0.05))` — счётный отступ вместо временного. Перекрытие окон индикаторов не закрыто.
4. **Нет проверки сопоставимости.** Не проверяется, что кандидат и baseline покрывают один временной интервал.
5. **Нет коррекции на множественные сравнения.** При ежедневной генерации кандидатов ложноположительное срабатывание гарантировано в пределах месяца.

### D6 — HIGH — Прогнозный слой без обучения и калибровки

`forecast_engine` содержит только B0 (персистентность) и B1 (дрейф, ограниченный ±5% за бар).

- `forecast_engine/core.py`: `confidence = Decimal("0.5") if model_version == "B0" else Decimal("0.55")` — константа, не калиброванная вероятность.
- `forecast_engine/evaluator.py`: только `mae` и `directional_accuracy`.
- `trader_v1_forecast_eval`: ровно те же две колонки.

Нет pinball loss, покрытия квантилей, Brier score, skill score против B0. Точность нечем измерить.

### D7 — HIGH — Backtest берёт данные с другого рынка

- `scripts/fetch_history.py`: `HTX_REST_URL = "https://api.huobi.pro"` — **спот**
- рантайм-коллектор: `api.hbdm.com` — **linear swap BTC-USDT**

Базис и фандинг делают результат backtest несопоставимым с боевым контуром.

### D8 — HIGH — Четыре ошибки в единственном живом «учителе»

`webui/app.py:2794-2880`:

1. `ORDER BY closed_at DESC LIMIT 100`, затем эквити накапливается в том же порядке → просадка считается по развёрнутой во времени кривой. Полученное число не является drawdown.
2. Порог значимости — 3 закрытые позиции.
3. Хардкод `"old": 200` для `max_leverage` при `MAX_LEVERAGE = 100` в `sim_math`. В chatbot-эвристике тот же параметр имеет `"old": 10`. Кандидат ссылается на несуществующее значение.
4. `sim_evaluations.max_drawdown DECIMAL(5,2)` (`chatbot/storage/postgres_client.py:85-95`), а пишется абсолютная сумма USDT → вставка упадёт при DD > 999.99.

### D9 — MEDIUM — Целевая функция из произвольных весов

`chatbot/services/plan_accuracy.py:161-170`: `accuracy_score` = аддитивная шкала 30 + 25 + 30 + 15. Веса ниоткуда не выведены и не связаны с P&L. Оптимизация по такой цели уводит от прибыли.

### D10 — MEDIUM — Cross-маржа принимается, считается как isolated

`open_position` принимает `margin_mode="cross"`, вся математика — isolated. Подтверждено внешним отчётом §6.2. Эпизоды с cross попадут в выборку с неверным PnL и неверной меткой ликвидации.

### D11 — MEDIUM — EMA предыдущего бара восстанавливается инверсией

`paper_trading/strategy.py:388-396`: `prev_ema = (E − α·p) / (1 − α)` вместо хранения предыдущего значения. При больших α и длинных сериях накапливается ошибка округления Decimal ровно в той точке, где принимается решение о входе. Ломает воспроизводимость replay.

## 4. Целевая архитектура

Два кольца с разной частотой.

**Быстрое кольцо (детерминированное, без LLM, на каждом закрытом баре):**

```
HTX linear swap → Candle Store → Feature Builder → Ансамбль (B0/B1/EMA-ATR/online-LR)
  → Калибровка → Сигнал + квантили → Risk gate → paper_v2 execution
  → Episode Builder → Метрики → обновление весов ансамбля → Ансамбль
```

**Медленное кольцо (с LLM, раз в сутки):**

```
Метрики → Qwen reflector → кандидат правил → walk-forward гейт (без LLM)
  → approved: strategy_versions.active → Ансамбль
  → rejected: обратно к reflector
```

Требование: быстрое кольцо не имеет права обращаться к LLM. Это ограничение по латентности и по бюджету одновременно.

## 5. Блоки реализации

Порядок обязателен: каждый блок опирается на предыдущий.

### Блок A — Слой данных (3–4 д, снимает D1, D7)

Единственный источник истины по цене — HTX linear swap. Спот не используется нигде.

1. Писатель свечей в `trader_v1_perp_candles` из коллектора: агрегация 1m из WS-тиков + сверка REST `market_history_kline` на `api.hbdm.com`.
2. Таймфреймы 1m / 15m / 1h / 4h. Старшие собираются из 1m детерминированно, отдельно не тянутся.
3. Backfill: переписать `scripts/fetch_history.py` на `api.hbdm.com`, загрузить минимум 180 суток 1m.
4. Датчик целостности: джоб поиска разрывов по `open_time` с дозагрузкой; метрика `candle_gap_count` в `/healthz`.
5. Таблица фандинга (`funding_rate`, шаг 8h) — иначе PnL удержания неверен.

**Критерии приёмки A:**
- `SELECT count(*)` по 1m за 180 суток ≥ 258 000 строк, разрывов 0.
- SHA-256 датасета стабилен между двумя последовательными прогонами.
- Свечи 1h, собранные из 1m, совпадают с REST 1h HTX до 1e-8 на 1000 случайных барах.
- Ни один модуль не обращается к `api.huobi.pro` (grep в CI).

### Блок B — Единая торговая математика (2–3 д, снимает D3, D10, D11)

Эталон — `sim_math.py` как более строгий: деление на `(1 − MM)` соответствует решению уравнения `equity = maintenance`.

1. Вынести в пакет `trading_math/`: `validate_order`, `liquidation_price`, `settlement`, `position_size`, `funding_accrual`.
2. `paper_trading/risk.py` и `chatbot/services/sim_engine.py` импортируют оттуда; локальные копии формул удаляются.
3. Cross-маржа: до реализации профильной формулы — `raise ValueError` в валидаторе с явным сообщением. Молчаливый расчёт по isolated запрещён.
4. Хранить `prev_ema` явным полем вместо инверсии рекуррентности.
5. Property-тесты (hypothesis): монотонность liq по leverage, симметрия long/short, `settlement` при `exit == entry` даёт ровно минус две комиссии.

**Критерии приёмки B:**
- Расхождение liq между контурами = 0 на сетке L ∈ [1..100] × direction × 10 000 цен.
- Существующие 390 тестов проходят без изменений ожидаемых значений, либо каждое изменение оформлено ADR.
- В дереве ровно одно определение `liquidation_price`.

### Блок C — Эпизоды и метрики (3 д, снимает D6, D8, D9)

1. Episode Builder: из `paper_v2_positions` и `sim_positions` в один `Episode` с обязательными `data_hash`, `features_hash`, `math_version`, `strategy_version`.
2. Метрики прогноза: pinball loss по q10/q50/q90, эмпирическое покрытие интервала, Brier score направления, skill score против B0. Расширить `trader_v1_forecast_eval`.
3. Метрики торговли: Sharpe и Sortino на дневных доходностях, просадка **кривой эквити в хронологическом порядке**, profit factor, средний R, доля ликвидаций, оборот комиссий.
4. Починить `POST /api/strategy/evaluate`: `ORDER BY closed_at ASC`; `max_drawdown → NUMERIC(20,8)`; убрать хардкод `old: 200`; минимальная выборка 30.
5. `accuracy_score` с произвольными весами вывести из приёмки. Целевая функция — net PnL с поправкой на риск.

**Критерии приёмки C:**
- Один эпизод, построенный из обоих контуров, даёт идентичный `net_pnl`.
- Просадка на синтетической кривой с известным ответом совпадает до 1e-8.
- Покрытие интервала q10–q90 на holdout попадает в 0.80 ± 0.05, либо блок E помечен как неоткалиброванный.

### Блок D — Статистически корректный гейт (4 д, снимает D5)

Переписать `LearningEvaluator` и подключить к рантайму.

1. Walk-forward с **временными** границами: purge = `max_lookback + max_hold`, embargo ≥ 1 бар старшего таймфрейма.
2. Тест значимости: bootstrap-ДИ разницы net PnL (≥ 10 000 ресэмплов) либо t-статистика по дневным доходностям. Гейт — нижняя граница 95% ДИ > 0.
3. Deflated Sharpe Ratio с поправкой на число протестированных кандидатов; счётчик испытаний в `paper_v2_strategy_versions`.
4. Минимумы: 200 эпизодов на обучение, 60 на holdout, 30 торговых дней покрытия.
5. Проверка сопоставимости: идентичный временной интервал у кандидата и baseline, иначе `status = "incomparable"`.
6. Гейт по риску: просадка эквити не хуже baseline, доля ликвидаций не выше, нарушений риска не больше.

**Критерии приёмки D:**
- Тест «шумовой кандидат»: 100 кандидатов из перемешанных меток → доля approved ≤ 0.05.
- Тест «заведомо лучший кандидат»: синтетика с edge +0.3% на сделку → approved.
- Утечка look-ahead ловится: сдвиг признака на −1 бар → гейт отклоняет.

### Блок E — Обучаемый слой (5 д, снимает D2, D4, D6)

1. Снять ограничение long-only: симметричные правила для short (`regime_bearish`, `confirm_15m` вниз, зеркальный триггер). Отдельная метрика по сторонам.
2. Ансамбль предикторов: B0, B1, EMA/ATR-моментум, онлайновая логистическая регрессия на признаках из `forecast_engine/features.py`. Веса — экспоненциальное взвешивание по скользящей pinball loss (Hedge / exponentiated gradient), обновление на каждом закрытом баре.
3. Калибровка: изотоническая регрессия направления на скользящем окне 30 суток. `confidence` перестаёт быть константой.
4. Consumer правил: `strategy_rules` со `status = 'active'` читается при старте стратегии и применяется к `BaselineV1Config`. Набор изменяемых параметров — белый список с жёсткими границами.
5. Промоушен `candidate → active` только через блок D. Прямая запись `active` из webui запрещается на уровне кода.

**Критерии приёмки E:**
- Веса ансамбля на holdout дают pinball loss ниже лучшего одиночного предиктора.
- Калиброванный confidence: эмпирическая частота в бакетах 0.5/0.6/0.7 отклоняется ≤ 0.05.
- Изменение `strategy_rules.status = 'active'` наблюдаемо меняет поведение стратегии в replay.
- Short-сделки присутствуют в выборке и покрыты тестами наравне с long.

### Блок F — Агент на Qwen Flash (3 д, медленное кольцо)

LLM участвует только в суточной рефлексии. Прав на исполнение нет.

1. Адаптер поверх существующего `OpenAICompatibleAdapter`, base_url `https://dashscope-intl.aliyuncs.com/compatible-mode/v1`, ключ из env.
2. **Слаг модели только из env.** Реестр моделей заполняется по живому ответу `/models` при старте.
3. Роль `reflector`: вход — метрики за сутки и активные правила, выход — строгий JSON по `output_schema`. Ответ вне схемы = отказ, не «парсинг на удачу».
4. Каждый вызов пишется в `trader_v1_agent_runs` с `input_hash` — одинаковый вход в одни сутки не оплачивается дважды.
5. Бюджет через `budget_policy`: потолок токенов в сутки; при исчерпании — детерминированная эвристика (`_heuristic_candidate` уже написан).
6. **Loop guard.** Детектор вырожденного вывода: повтор одного токена/символа подряд > 32 раз (в частности `!`) → вызов аборти­руется, помечается `status = "failed"`, включается эвристика. Watchdog-таймаут на вызов — 120 с. Связка SGLang + thinking + `--tool-call-parser qwen3_coder` запрещена (см. §6.2).
7. `presence_penalty = 0.5…1.0`, `reasoning_effort` фиксирован на уровне роли, context cache включён на системный промпт и определения инструментов.

`TABLE: Agent roles — copy to Sheets`

| role | frequency_per_day | model_class | output_type | on_failure |
|---|---|---|---|---|
| reflector | 1 | flash | json_schema | heuristic |
| reviewer | 1 | other_vendor | approve_reject | skip |
| explainer | on_demand | flash | text | template |
| gate | per_candidate | none | deterministic | none |

**Критерии приёмки F:**
- Смена слага модели через env не требует изменений кода.
- Повтор вызова с тем же `input_hash` не создаёт нового платного запроса.
- Ответ, не проходящий `output_schema`, не попадает в `strategy_rules` ни при каких условиях.
- Суточный расход токенов виден в `ai_usage_log` и не превышает лимит.
- Loop guard срабатывает на синтетическом вырожденном ответе и переводит вызов в эвристику, не вешая контур.
- Reliability tool-call на собственном многоходовом харнессе ≥ 0.95, иначе фиксируется эскалация на более крупную модель.

### 6.2 Риски модели и как они закрываются в ТЗ

1. **Подтверждённый баг зацикливания.** Issue `sgl-project/sglang#36537`: детерминированный цикл повтора token-ID-0 (декодируется как `!`) при одновременном thinking + хотя бы один OpenAI-совместимый tool + SGLang с `--tool-call-parser qwen3_coder`.
   → **Запрет на эту связку.** Идти через production API QwenCloud либо vLLM. В оркестраторе — детектор повторяющихся токенов и watchdog-таймаут на вызов.
2. **Склонность к повторам.** Карточка модели рекомендует `presence_penalty` 0–2, но высокие значения дают смешение языков.
   → Фиксируем `presence_penalty = 0.5…1.0` для роли `reflector`, валидация JSON против схемы на стороне оркестратора обязательна.
3. **Thinking-токены тарифицируются как выход**, а смена `reasoning_effort` сбрасывает весь KV-кэш.
   → `reasoning_effort` фиксируется на уровне роли и не меняется в пределах суток. Context cache — на системный промпт и определения инструментов.
4. **HLE 35.9** — модель уступает топам в сложном численном и мультидисциплинарном рассуждении.
   → Подтверждает ADR-03: вся численная логика (PnL, ликвидация, метрики, гейт) остаётся в детерминированном коде. LLM не считает — LLM предлагает гипотезу.
5. **Зрелость релиза.** Qwen позиционирует веса как намеренно недообученное превью архитектуры Qwen4.
   → В реестре моделей держать альтернативный default (GLM-5.3-Flash или текущий `glm-5.2`) и переключать через env без правок кода. Это уже поддержано архитектурой шлюза.
6. **BFCL и Tau-bench для модели не опубликованы** — независимой метрики надёжности tool-call нет.
   → Мерить своим харнессом. Порог: reliability tool-call на многоходовых сценариях ≥ 0.95, иначе эскалация на `qwen3.8-max` или смена default.

**Практическое следствие:** блоки A–D детерминированные и от LLM не зависят. Начинать с них. Блок F имеет смысл только после них — агенту нечего рефлексировать, пока нет ни данных, ни честных метрик.

## 9. ADR

### ADR-01 — Эталон математики ликвидации: sim_math

**Контекст.** Две расходящиеся реализации (D3).
**Решение.** Эталон — формула `sim_math` с делением на `(1 − MM)`; `risk.py` приводится к ней.
**Обоснование.** Деление на `(1 − MM)` — результат решения уравнения `equity = maintenance requirement` с учётом taker-fee на входе; аддитивная форма `risk.py` — линейная аппроксимация того же уравнения, точная только при `MM → 0`.
**Последствия.** Ожидаемые значения части существующих тестов `paper_trading` сместятся; каждое смещение фиксируется в приёмке блока B.

### ADR-02 — Самообучение без дообучения весов модели

**Контекст.** Бюджет $20–30/мес, local-first, отсутствие GPU-контура.
**Решение.** Обучение = адаптация весов ансамбля (Hedge) + изотоническая калибровка + in-context рефлексия LLM.
**Обоснование.** Детерминированно, воспроизводимо, проверяемо тестами; не требует инфраструктуры обучения; согласуется с принципом проекта.
**Последствия.** Потолок качества ниже, чем у обучаемой end-to-end модели. Принимается осознанно в пользу верифицируемости.

### ADR-03 — LLM исключён из быстрого кольца

**Контекст.** Решение о входе принимается на закрытии 1m-бара.
**Решение.** LLM вызывается только в суточном цикле. Сигнал и риск-гейт — детерминированный код.
**Обоснование.** Латентность, стоимость, воспроизводимость replay. Недетерминированный компонент в горячем пути делает walk-forward невоспроизводимым.
**Последствия.** LLM влияет на поведение только через прошедший гейт кандидат правил.

### ADR-04 — Политика плеча ≤ 100x как зеркало лимита HTX

**Контекст.** Открытый FAIL §16.2 нормативного ТЗ (требование «только плечо выше 100x»).
**Решение.** `MAX_LEVERAGE = 100` фиксируется как отражение фактического лимита HTX на BTC/USDT perp; требование ТЗ признаётся дефектом документа.
**Обоснование.** Буквальное исполнение физически нереализуемо на целевой бирже.
**Последствия.** Требуется addendum к нормативному ТЗ, иначе внешний аудит по документу будет давать FAIL бессрочно.
