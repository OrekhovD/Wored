# WORED WebUI: аудит удобства и ТЗ для QODER (QWEN3.8flash)

Дата: 2026-09-26. Статус: предложение к реализации, код приложения не изменён.

## 1. Цель, границы и доказательства

Сделать WebUI понятным пультом управления симуляционной торговлей: пользователь за один маршрут видит состояние дня, раздельные ручной и автоматический счета, причину действий автомата, итог с расходами и состояние обучения. Сохранить исследовательские и инженерные функции без конкурирующих центров управления.

Проверено в этом аудите: маршруты, шаблоны, JS и API текущего checkout; браузерный проход изолированного `tests.ui.fixture_app` на `127.0.0.1:18080`; страница входа защищённого WebUI на `127.0.0.1:8080`. Доступ к Docker API отклонён ОС; рабочие страницы 8080 возвращают редирект на вход. Операции на рабочем runtime, реальные сделки, отчёты БД и Telegram **не проверены**. QA fixture отличается от приложения: в нём нет `/trading-day`, а `/trader` заявлен в списке, но отдельный route handler отсутствует. Ошибки fixture нельзя автоматически переносить на production.

Нормативные ограничения: `AGENTS.md` (инкрементальный WebUI, сохранение маршрутов и chart containers, запрет несанкционированных runtime-мутаций) и `docs/TRADING-DAY-PIPELINE-RFC.md` (два независимых счета, поток «Сегодня → Итоги → Обучение», единый сервис команд и доказательный учет).

## 3. Приоритетные проблемы

1. **P0 — конкурирующие финансовые действия.** `trading_day.html` + `trading-day.js` используют `/api/paper/accounts/.../orders`; `command_deck.html` использует `/api/positions/open`, а `daily_session.html` запускает свой lifecycle. Возможны разные правила риска, учета и attribution. До унификации не называть любое из представлений «единым».
2. **P0 — доверие к состоянию.** В `paper_api.py` domain branch для отсутствующего дня возвращает `proto-manual`/`proto-auto`, `fresh: true`, `engine_status: running` и фиксированные суммы. При ошибке domain вызова код молча переходит к legacy. UI обязан показывать источник и качество, запрещать действия при непроверенной готовности. Не превращать fallback в зелёную готовность.
3. **P1 — нет самостоятельных «Итогов» и «Обучения».** Блок `renderReport` показывает краткие realized net/fees/win rate и candidate review; отсутствует адресуемая история дня, детализация ledger/funding/slippage и решение по кандидату. Это проектный разрыв, а не доказанный баг существующего API.
4. **P1 — избыточная навигация и повтор данных.** Шапка содержит 12 ссылок; `/`, `/system`, `/trader`, `/command-deck` повторяют health/market/positions. В браузере главная открывается с крупным графиком, админ-действиями и несколькими информационными колонками до ответа на вопрос «что делать сейчас».
5. **P1 — неработающие админ-кнопки в `/system`.** Исправить action paths, проверить CSRF и ролевые права; не запускать их на рабочем runtime в рамках UI-аудита.
6. **P1 — неверный status indicator в общей шапке.** `navigation.html` создаёт `id="dataStatus"`, `base.html` обновляет отсутствующий `dataStatusLabel`; `navAlertBadge` также не создан. Пользователь видит «—» вместо свежести. Устранить несовпадение и показывать возраст данных, а не только цвет.
7. **P1 — несоответствие QA стенда.** `fixture_app.py` не обслуживает `/trading-day`, `/trader` и полный candle contract. В браузере `/` показал `Web UI bootstrap failed: Cannot read properties of undefined (reading 'length')`; Command Deck показал `Режим undefined`; стратегия — `undefined%`. Лог стенда также подтвердил 404 для `/api/daily-session/list`, `/api/sim-positions`, `/api/strategy` и `/api/strategy/positions`. Это блокирует честную UI-приёмку.
8. **P2 — терминология и плотность.** На русских страницах используются `Launch`, `Snapshot`, `Open`, `Trader`, `Re-evaluate`, `Net`, `LIVE` без единого словаря. Диагностические и вторичные KPI выводятся на один уровень с финансовым состоянием.

## 4. Целевая информационная архитектура

Главная навигация: **Сегодня | Итоги | Обучение | Ещё**. В «Ещё»: Рынок, Прогнозы, Оповещения, Журнал, Система (включая Модели). Настройка дня открывается в контексте «Сегодня». Для инженера доступен раскрываемый диагностический слой; обычный пользователь видит только воздействие на торговлю и рекомендуемое действие.

| Старый экран | Решение | Новое назначение |
|---|---|---|
| `/trading-day` | Канонический маршрут «Сегодня» | День, два счета, ручная заявка, автомат, позиции, события. |
| `/command-deck` | Сохранить URL, убрать независимый ticket и POST; вести в «Сегодня» с якорем/режимом панели | Компактное представление тех же данных, если оно реально нужно после user test. |
| `/daily-session` | Сохранить URL; вести к состоянию/плану автомата в «Сегодня» | Legacy deep link без второго старта дня. |
| `/trader` | Сохранить URL; оставить диагностический auto-detail только при достоверном источнике | План, режим агента и решения, без конкурирующего контроля. |
| `/futures-lab` | Сохранить URL; перенести историю позиций в «Итоги» | Архив старой симуляции явно маркировать по источнику. |
| `/strategy` | Сохранить URL; перенести проверенные правила в «Обучение» | Аналитика/история оценок, не управление активной версией задним числом. |
| `/` и `/dashboard` | Сохранить маршруты как «Рынок» | Chart, watchlist, alerts; админ-действия убрать в «Система». |
| `/predictions`, `/alerts`, `/journal` | Сохранить и связать контекстными ссылками | Исследование, triage, evidence. |
| `/system`, `/model-management` | Сохранить, объединить доступ через «Система» | Health, readiness, models, административные действия. |

Новые адресуемые страницы: `/results` (последний и история дней), `/results/{day_id}` (финальный или ожидающий отчет), `/learning` (список наблюдений/кандидатов), `/learning/{candidate_id}` (evidence, валидация, решение). До готовности backend показывать честное «Функция ещё не доступна», без фиктивных данных и кнопок применения.

## 5. Точный контракт экранов

### 5.1 «Сегодня»

Верхняя строка: статус дня, время окончания с часовым поясом, источник/возраст рынка, качество симуляции и одно главное следующее действие. Ниже две симметричные карточки **Ручной счёт** и **Автомат**: отдельные `account_id`, equity, доступная маржа, net P&L после расходов, остаток лимита, позиции. Вкладки «Позиции», «Заявки», «События» фильтруются по счету и показывают origin/intervention. Автомат отдельным блоком: состояние, причина ожидания/блока, условия следующей проверки, версия плана и последняя команда. График HTX содержит оси цены/времени, источник, mark/bid/ask по назначению, возраст данных и реальные уровни позиций; chart containers price/volume/RSI/MACD сохраняются.

Ручная заявка: направление, тип, риск, плечо, обязательный стоп, необязательная цель. Preview обязателен и подписан временем/источником/сроком действия; отображает bid/ask fill, mark risk, quantity, margin, fees entry/exit, funding если известен, slippage, break-even, net TP/SL, liquidation quality и причины запрета. Перед отправкой зафиксировать account_id, day_id, quote version и idempotency key. Ответ `202` означает «принято к исполнению», не «открыто»: показывать `command_id` и опрашивать результат. Unknown outcome уточнять по тому же ID, POST не повторять без проверки.

Пауза новых входов, продолжение, закрытие auto-позиций и завершение дня имеют отдельные последствия и подтверждение с конкретным счётом, числом позиций, оценкой расходов и финальным состоянием. Недоступное действие показывает причину и путь восстановления. Никаких «зелёных» статусов из демонстрационного fallback.

### 5.2 «Итоги»

Список по локальной дате, статусу `pending/preliminary/final/failed`, версии, качеству рыночных данных и статусу reconciliation. Деталь: ручной / автомат / разница. Строки: opening/closing equity, gross/net realized, unrealized на cutoff, fees, funding, оценка slippage без двойного вычета, доходность, max drawdown, число сделок, win rate при `N>0`, время экспозиции, нарушения лимитов, вмешательства. Каждая сумма раскрывается до order/fill/ledger ID. Ноль сделок показывать как `N=0` и «недостаточно данных» для win rate. Не показывать final, пока не закрыты/учтены оба счета. Экспорт JSON/HTML включает версию, cutoff, quality, политику и сверку; повторное скачивание не меняет данные.

### 5.3 «Обучение»

Раздельные карточки «Наблюдение», «Кандидат», «Проверяется», «Готово на завтра», «Применено», «Отклонено/отложено». Для каждой: проблема, evidence trade IDs и размер выборки, старая/новая версия правила, разрешённый параметр, replay + holdout + shadow result, ожидаемый net/risk эффект и условия отката. До отдельного backend-контракта это read-only список фактических `build_learning_review` наблюдений; **не** показывать кнопку «Применить» для `ready_for_validation`. Применение возможно только после серверной проверки, решения владельца и на следующий день. AI-ошибка не меняет финансовый отчёт.

### 5.4 «Ещё» и система

Рынок показывает графики и свежесть; Прогнозы — факт vs прогноз, горизонт и покрытие моделей; Оповещения — фильтр, severity и acknowledge; Журнал — trace решения и связанный день/сделка. Система показывает dependency health и отдельную execution readiness, возраст источника и время проверки. Probe моделей запускается явно; конфигурация, доступность, quota и активный маршрут не смешиваются. Админ-действия только для `can_admin`, с CSRF, объяснением эффекта, результатом и ссылкой на журнал; destructive clear подтверждается количеством затронутых записей.

## 6. Backend и UX-состояния

Перед реализацией UI QODER обязан составить таблицу `endpoint → owner/account/day source → schema → freshness → error/permission states` для `/api/trading-day/*`, `/api/paper/*`, `/api/daily-session/*`, `/api/command-deck`, `/api/strategy/*`, `/api/sim-positions`, `/api/health`, `/readyz`. Не объединять разные финансовые источники арифметически. Отсутствующие `/results`/`learning` API оформить как отдельный backend dependency с точным schema contract и безопасным read-only UI до его выполнения. Любая write-команда — через единый paper trading service, с owner check, CSRF, idempotency, command status и server-side risk validation. Не подменять actual balance данными `proto-*`.

Обязательные UI-состояния каждой карточки: loading, empty, fresh, stale, blocked, error, pending command, completed command. Цвет сопровождается текстом, timestamp и доступным действием. Автообновление останавливать на скрытой вкладке и возобновлять с повторной проверкой состояния; SSE/poll не должен менять решения пользователя или дублировать POST. После reconnect восстанавливать серверное состояние, не локальный optimistic P&L.

## 7. Порядок работ и файлы для QODER

Работать малыми patch-блоками с `PLAN → DIFF → APPLY → TEST → REPORT`. Перед каждым блоком назвать active runtime path, файлы, риск и проверку; не менять `.env`, Compose, chatbot/collector и БД в рамках UI-работы без отдельного задания. Не удалять `app.js`, существующие страницы и маршруты; не переписывать `styles.css` целиком. Сохранить dark command surface, orange accent, green ok, red risk, blue chart line; плотную операционную иерархию без hero-блоков.

1. **P0, достоверность и fixture:** исправить `webui/templates/base.html`, `partials/navigation.html`, `system.html`; обновить `tests/ui/fixture_app.py`, `tests/ui/fixture_data.py`, адресные `tests/ui/*`. В fixture добавить `/trading-day` и правильный `/trader`, полный `/api/candles` contract, согласованные прогнозные роли, статусы и суммы. Отдельно проверить реальные server responses; fixture не является runtime acceptance.
2. **P0, один центр действий:** `webui/templates/trading_day.html`, `webui/static/ui/trading-day.js`, `webui/templates/command_deck.html`, `webui/templates/daily_session.html`, `webui/templates/trader.html`, `webui/app.py`, `webui/paper_api.py` — убрать конкурирующие POST из старых UI, оставить deep links и единый command flow. 3. **P1, итоги и обучение:** добавить templates и UI modules для `/results` и `/learning`; read routes и presenters в `webui/app.py`/новых read-only модулях. Если данных ledger/candidate decision пока нет — сделать dependency явной и оставить безопасное пустое состояние. Не фабриковать отчет, funding или качество в frontend.
