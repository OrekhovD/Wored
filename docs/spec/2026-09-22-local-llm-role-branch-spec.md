# Spec: локальная роль в движке прогнозов (`ollama_local`)

Восстановлен 2026-09-22 после утраты оригинала при переписывании истории.
Написан по фактическому коду `webui/prediction_engine.py` в дереве `ee325e0` +
`c2fe3bf`, а не по памяти о первоначальной версии документа.

## Цель и граница

Рабочая станция отдаёт одну или несколько ролей прогноза локальному серверу
Ollama (`bonsai-27b` на порту `8088`), не трогая облачные цепочки по умолчанию.
Ветка чисто opt-in: при пустом `LOCAL_LLM_ROLES` поведение движка не меняется
ни на байт. Это отдельный `ollama serve` на хосте, он не имеет отношения к
Ollama Cloud (`https://ollama.com/v1`).

## Переключатели

| Переменная | По умолчанию | Значение |
|---|---|---|
| `LOCAL_LLM_ROLES` | пусто (= выключено) | список ключей ролей через запятую или `all`; читается на каждый вызов, тумблер без перезапуска модуля |
| `LOCAL_LLM_MODEL` | `bonsai-27b` | id модели на локальном сервере |
| `LOCAL_LLM_BASE_URL` | `http://127.0.0.1:8088` | из контейнера нужно `http://host.docker.internal:8088` |
| `LOCAL_LLM_TIMEOUT` | `120` | собственный бюджет: холодная загрузка 27B ~11 с, прогноз ~20 с в облачные 20–90 с не помещаются |

Пустая `LOCAL_LLM_MODEL` или нечитаемый `LOCAL_LLM_TIMEOUT` не роняют вызов:
кандидат просто не создаётся / берётся дефолт бюджета.

## Поведение

1. **Локальный кандидат возглавляет цепочку** — `_build_runtime_candidates`
   возвращает `[local, *cloud]`. Облако остаётся fallback: при ошибке локали
   роль уходит в обычную облачную последовательность.
2. **Транспорт — нативный `/api/chat`**, а не OpenAI-совместимый
   `/v1/chat/completions`: суффикс `/v1` срезается от base URL, авторизации нет
   (`api_key_env=""`), провайдер помечен `ollama_local` и в диспетчер вызова, и
   в расписание попыток.
3. **Thinking выключается только полем `think` верхнего уровня запроса.**
   Внутри `options` поле игнорируется, `reasoning_effort` этой модели ничего не
   меняет; без выключения весь бюджет уходит в рассуждение и `thinking-off`
   нельзя запечь в производную модель через Modelfile (`think` отваливается как
   unknown parameter) — единственная рабочая точка передачи = per-request.
4. **Контракт ответа повторяется после контекста.** Модель на коротком бюджете
   перестаёт держать формат, заданный в system-части, поэтому требования к JSON
   продублированы в последнем сообщении.
5. **Локальная попытка не ретраится на месте** —
   `_candidate_attempt_schedule` возвращает `(0.0,)` для `ollama_local`:
   очередь убивает попытку по `ATTEMPT_TIMEOUT_SECONDS = 300`, три ретрая по
   120 с умерли бы в полёте и увели вместе с собой облачный fallback.

## Проверка

- 8 тестов ветки + 3 теста калибровки в `tests/stabilization/test_contracts.py`;
  гейт: `docker compose -f docker-compose.qa.yml -p wored-qa run --rm --build
  checks pytest tests/ -q -p no:cacheprovider` → 829 passed / 20 skipped /
  1 xfailed / 5 failed (разбор пяти — в `docs/OPERATIONAL-PROCESS.md` §2).
- Живой контейнер: `import prediction_engine` в `webui` содержит `ollama_local`,
  маршруты `/`, `/alerts`, `/predictions`, `/journal`, `/daily-session` → 200.
- Калибровка уверенности в рантайме:
  `_calibrate_confidence(50.0, 'bull', 40.0)` → `41.0`.

## Что здесь сознательно не сделано

- Нет кеша исторической точности роли: один aggregate-запрос на вызов роли,
  не на попытку кандидата.
- Локальная модель не участвует в строгих NVAPI-проверках и не считается
  доступной по облачным критериям листинга.
- Судя по данным прод-БД, историческая калибровка пока может коснуться только
  роли `neutral` — причина в метрике, а не в этом пути (см. Q-3 в
  `docs/TASKS-QUEUE.md`).
